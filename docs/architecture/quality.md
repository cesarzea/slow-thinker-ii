# Quality requirements and acceptance scenarios

**Status: Proposed verification criteria for recorded requirements.** These are acceptance specifications, not passing test results. The [engineering baseline](../../README.md#engineering-standards) remains mandatory in full.

## Quality priorities

1. Extensibility without bypassing platform control.
2. Inspectable evidence and accurate spending attribution.
3. Bounded execution with explicit failure behavior.
4. Comprehensible visual representations and reproducible experiment definitions.
5. Modular implementation with enforceable engineering rules.

## Scenarios

| ID / requirement | Stimulus and context | Required response and verification |
| --- | --- | --- |
| QA01 / R02–R03 | Register a new conforming component in a running development installation. | Launch it in an independent local process and invoke it through public contracts without changing core domain code. Verify with a separately authored component fixture. |
| QA02 / R04, R17 | Select each bundled example, including the five-activation sequence that reuses two agents. | Derive its graph and execution order from the selected definition; accept valid references and reject missing targets, incompatible profiles, and out-of-order input dependencies before dispatch. Verify all four examples and invalid variants through the same validator. |
| QA03 / R05–R06 | A component calls an operation absent from its granted permissions. | Record rejection and make zero calls to the target. The discovery view must also exclude the capability. Verify both paths independently. |
| QA04 / R10 | Two callers reach one sequential component while independent components also have work. | No overlapping activation within the serialized scope; independent scopes remain eligible. First-cycle unsupported modes must fail validation, not run with altered semantics. |
| QA05 / R11–R12 | A component reports reasoning or state, and another supplies no such information. | Display reported evidence with provenance; explicitly mark unavailable evidence. An inference must not be displayed as a platform-observed event. |
| QA06 / R14 | Concurrent requests each fit the remaining budget, but their sum does not. | Atomic authorization prevents over-reservation in every scope. Verify with controlled interleavings, including nested resource calls. |
| QA07 / R14–R15 | A call is cancelled after provider acceptance, then usage arrives later. | Keep unsettled obligations, record late usage once, and reconcile without resuming the run. Verify duplicate usage delivery and timeout cases. |
| QA08 / R13 | A request produces progress events but never completes. | The configured absolute deadline still expires; no progress event can extend the run beyond its limit. Verify with a controllable clock. |
| QA09 / R14 | An operation cannot supply a trustworthy maximum charge, or the conservative reservation exceeds remaining funds despite a smaller likely cost. | Refuse dispatch; do not substitute estimates, zero or a higher cap. Show reserve versus charge, verify boundary equality and confirm no external invocation. For the proposed OpenAI policy, cover both tariff bands and capacity/output-cap violations. |
| QA10 / R16, R20 | The operator closes the browser and later reopens it. | Backend execution continues; the same saved session and run are inspectable. Verify a browser reconnection journey. |
| QA11 / R16 | Backend crashes with active calls and reserved money. | On restart, mark execution interrupted, preserve unsettled accounting, and make zero automatic paid replays. Verify each chosen persistence boundary. |
| QA12 / R18–R19 | Inspect proposer → reviewer → proposer revises. | Show two agent identities and three activations; model-resource calls are identifiable; the final input visibly includes the original proposal and review. |
| QA13 / R18–R19 | A graph exceeds available view space or has overlapping nodes. | Keep identities stable and permit layout reorganization. Verify inspection remains possible without confusing control flow and observed communications. |
| QA14 / R08 | A separate component process makes a nested model call through supported OpenAI and LangChain interfaces, including use inside a LangGraph node, and calls an authorized MCP/tool operation. | Preserve ordinary invocation signatures, native response details and parent-activation correlation. Exercise the provider request/response/error matrix, platform denial and timeout mappings, both client directions and zero hidden retries; charge billable attempts once. |
| QA15 / R09 | Two agents use the same plugin type but different configured resource instances. | Do not share state implicitly. Explicitly shared bindings refer to one resource identity and declared concurrency policy. |
| QA16 / R22 | Introduce an import of private module internals, `any`, dead code, or an over-complex unit. | The corresponding quality gate fails locally and in CI. A passing build cannot rely on weakening the rule. |
| QA17 / R23 | Model spending by Slow Thinker II and the original executor using the same provider account. | Only managed II attempts affect II run, session and monthly totals. Budget labels identify this scope and make no provider-account cap claim; no original-executor integration is required. |
| QA18 / R24–R26 | Later compare graph variants with different model/settings or evaluation inputs. | Preserve these differences and evaluation-policy versions; never present an uncontrolled comparison as proof of one graph's superiority. |
| QA19 / R27 | B 1.2.0 and B 2.0.0 become available while A installations pin B 1.1.0 or allow B 1.x. | Preserve existing resolutions. An explicit update keeps the exact pin fixed and may select 1.2.0 for the compatible range, never 2.0.0. Verify historical resolution retention, transitive constraints, cycle rejection and mediated calls from inherited code when inheritance is implemented. |
| QA20 / R28 | Later export a supported graph and execute it with the platform unavailable, using the same deterministic component/provider fixtures. | Verify functional control/data flow, requests, outputs and side effects on paths unaffected by platform supervision. Assert direct calls and absence of platform logging, intermediation, accounting and supervisory checks. Report unsupported dependencies; retain build provenance and benchmark overhead. Platform stop behavior is deliberately excluded from equivalence. |
| QA21 / R29 | Feed text, valid JSON, malformed JSON, schema-invalid JSON and an unknown-reference review through LLMCall; also return refusal, null content and parseable JSON marked incomplete. | Verify response eligibility before parsing, exact raw-response retention, one provider attempt, effective instance-schema enforcement, MCP error signaling, no downstream activation on unhandled failure and retained usage charges. Documentation fixtures validate proposed data shapes; they do not prove these runtime outcomes. |
| QA22 / R03, R05, R08–R10 | Add a tool and a memory component in a later cycle; let stateless agents use private and explicitly shared memory, then close a run. | Verify component-specific operations, mediated access and complete call inspection without requiring LLMCall inheritance. Binding alone must not inject context. Check access isolation/sharing and that host shutdown preserves data declared persistent. Reject unsupported lifecycle modes before dispatch. These are extension acceptance criteria, not implemented capabilities. |
| QA23 / R02, R10, R13, R15–R16 | A required host fails readiness, a stop races with completion, or owned-process cleanup fails. | Exercise the lifecycle/transition proposals: no graph activation before readiness, no admission after stop/deadline, no automatic restart/replay, retained primary cause, and visible cleanup/settlement status independent of the run outcome. |
| QA24 / R05–R08, R11 | A reused host invokes proposer for draft then revision, sends old authority, supplies another caller identity, or returns while a child remains active. | Verify fresh LLMCall objects/clients with one stable configured identity and no implicit history. Reject stale/forged authority, preserve causal identity and apply the parent/child failure policy. Keep normal SDK signatures; cleanup must occur on success, failure and cancellation. |
| QA25 / R11–R16 | Exercise accounting cases AP01–AP10 and crash boundaries T1–T5; force a lock timeout, disk failure, migration failure or stale backup restoration. | Preserve exact amounts, period identities, atomic reservations and one charge per attempt. Dispatch only after durable authorization; retain ambiguous obligations, refuse unsafe recovery and perform no automatic paid replay. Verify both database contents and the external-call count. |
| QA26 / R11–R12, R18–R19, R25–R26 | Inspect nested calls and repeated activations with missing internal reports, redacted/oversized payloads, cancellation and a late response. | Reconstruct effective inputs and causal calls with stable identities. Keep receipt distinct from truth, reported explanation distinct from inference, and missing content distinct from empty content. Preserve terminal outcomes on late delivery, expose recording gaps and stop on capture failure. |
| QA27 / R16–R20 | Navigate the four examples and repeated participants; race duplicate Starts, command withdrawal, two tabs and lost replies; page events during execution and change a shared budget without a run event. | Verify one admitted run per intent, durable receipts/tombstones and no automatic replay. Preserve identities/selection through reflow; refresh complete projections, inspect consistent pages and reject foreign object references. Exercise the list/keyboard path and operator API acceptance cases. Numeric targets remain Q18. |
| QA28 / R02, R21–R22, R27 | Apply the deliberate import, cycle, private-entry, development-dependency and misplaced-file violations in the module-boundary proposal. | Every violation fails the corresponding local and CI gate. Domain modules remain independent of frameworks/adapters, component packages remain independent of backend internals, and the location manifest rejects undeclared source placement. |

## Numeric measures still to select

Graph size, live-status delay, validation latency, maximum payload size, retention period, maximum schema complexity and cancellation grace period require explicit targets before the applicable implementation. Accounting precision has a concrete proposal under Q07. No arbitrary performance promise has been introduced.

Configurable deadlines and budgets are measured against the effective profile saved with the run. The [accounting policy](../contracts/accounting-policy.md) proposes admission at exact equality and explicit rounding/period rules; those semantics await review.

## Closure evidence

The specification review checks coverage from requirements to scenarios and decisions. Implementation evidence must later identify the executing test or gate, the supported environment, and its outcome. Coverage percentages alone do not establish semantic correctness of accounting, authorization, or graph evaluation.
