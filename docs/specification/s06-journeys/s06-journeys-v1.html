The model in eight terms

These are the only concepts a user meets in step 1. Permissions never appear: a connection, or the choice of a model, is itself the authorization. The platform mediates and records every call.

Graph

A versioned definition of nodes and connections, with limits: activations, running nodes, time and budget per run.

Node

An instance of a component with its own configuration. It does not know where its output goes.

Port

A named input or output of a node. An LLM Call has in and out; a Router's outputs are the names you declare.

Connection

From an output port to an input port. It is the only path a message can take.

Message

What travels on a connection: text or JSON. Messages are asynchronous; one output connected to several nodes reaches all of them at once.

Activation

One execution of a node for one received message. Stateless nodes may run several activations at the same time.

Embedded component

A component placed inside a node, here a Router at the node's output. The user sees one node; the platform runs both.

Platform service

Something the platform provides, such as the configured LLMs. Calls to services are synchronous and also recorded.

Journey 1 · step 1.1

One agent makes a story funny

The smallest useful graph: a trigger sends a one-line story, one LLM Call rewrites it, the result arrives at an Output.

  1. Open Graphs, choose New graph and name it “Funny story”.
  2. Drag Trigger, LLM Call and Output from the palette. Rename them Story, Proposer and Funny story.
  3. Drag from Story's out to Proposer's in, then from Proposer's out to Funny story's in.
  4. Select Proposer. The side panel shows read-only summaries; until a model is chosen it says “Model not selected” and Run is disabled with that reason.
  5. Choose Edit. In Prompt, write the instructions. In Model, pick an LLM; its parameters appear below it. Choose Apply.
  6. Select Story, choose Edit and write “A cat tried to learn to fly.”.
  7. Choose Save. This creates version 1; runs always keep the version they used.
  8. Choose Run. The run dialog shows the trigger's message, editable for this run. The run completes and the result appears under Funny story.

Journey 2 · step 1.1

An agent gains two outputs with an embedded Router

A judge scores the story and an embedded Router sends it to “Funny” or “Not funny”. The node stays one node; no wrapper or extra node appears anywhere.

  1. Create “Story triage” with Story → Judge (LLM Call). Judge's prompt asks for a score from 1 to 10; its output format is JSON with an integer score.
  2. With Judge selected, choose Add component. Only components that can be embedded at a node's output are offered; choose Router.
  3. Judge's dialog gains a Router section, declared by the Router component. Declare the outputs funny and not_funny and write the script.
  4. On the canvas, Judge's single out port is replaced by funny and not_funny. Connect them to two Output nodes.
  5. Run. The story arrives at exactly one of the two outputs, with the content the script returned.
  6. To undo, choose Remove component in the Router section. The node returns to one out port; the dialog lists the connections that will be removed before you confirm.

Script 
def route(received, node_input):
    # received: what the LLM Call produced, here {"score": 8}
    # node_input: the message that activated this node
    if received["score"] >= 7:
        return "funny", node_input
    return "not_funny", node_input
Must return an output name declared above and the content to send through it. Any other result fails the activation with a recorded error.

One dialog per node. Its sections come from LLM Call's declaration plus the embedded Router's declaration, marked “embedded”. The script receives the LLM Call's result and the node's input, and returns two values: the output and what to send.

Journey 3 · step 1.1

A review loop until the story is funny enough

Proposer rewrites the story; Reviewer scores it. Its Router accepts the story or sends it back for another rewrite. The activation limit guarantees the loop ends.

  1. Build Story → Proposer → Reviewer. Embed a Router in Reviewer with outputs accepted and revise.
  2. Connect accepted to an Output named “Funny story” and revise back to Proposer's in.
  3. Open Limits: maximum activations 10, maximum running nodes 4, time limit 120 s, budget $0.05 per run.
  4. Save and run. A typical run shows Proposer twice and Reviewer twice before the story is accepted.
  5. If the story is never accepted, the run stops at the activation limit with the status “Stopped: activation limit reached”. Everything that happened remains visible.

Where the screens come from

Yes, as you described: what the interface shows for a component is defined inside that component's package. The platform reads the declaration and builds the summaries and dialogs with its own generic controls: text, multiline, number, choice, list, code, schema and service. Components never ship interface code. Ports and embedding positions are declared in the same package, beside the presentation.

The service control is what makes the model section work: it lists the platform's LLMs and renders the selected provider's parameter schema inline. Anything a component does not declare falls back to a form generated from its configuration schema.

The saved graph for journey 3

The graph is saved as one typed document. It contains what the user built and nothing else: no permissions, wrapper nodes or internal identifiers. The platform derives authorizations from the connections and the model choices.

What the platform records in every run

Supervision and recording are on by default for every interaction. A pass-through mode may come later. Components add what they want analysed through reports; the predefined components report their internal steps.
